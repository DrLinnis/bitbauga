# Recipe docs!

A recipe can describe multiple things, but often time, it expresses a piece of code or a resource. With recipes you can unpack files, build a library (both internal and external), and define applications. The philosophy of a recipe is to build or unwrap a piece of *package* once, but other recipes that depend on said recipe, can connect dependencies to a subsection of the *package*. This means that a single recipe can potentially build multiple examples or tests to a single library, but they still might not end up in the final application.

The output of a single recipe is a package. The default package generated by a recipe has the same name as the recipe itself.

## Helpers
To help define recipes, one can reuse recipe-code by utilizing `classes` or `include` files (`.bbclass` and `.inc` respectivly).

## Name
Each recipe is named on the format of `reciepename_version.bb` expressed as `${PN}_${PV}.bb`.

### Package Name
This is the name of the recipe, without the version of file extension. It can be accesed inside of a recipe as `${PN}`

### Package Version
This is usually configured as some sort of number, e.g. `1.2.4`, but can also bet set as `git` for recipe versions that are set differently. It can be accesed inside of a recipe as `${PV}`

## Dependencies
There are three major ways a recipe can depend on other files. They are `parsing`, `build`, and `runtime` dependencies.

### Parsing directives
In order to more easily define a recipe and reuse common definitions, a recipe can `inherit`, `include`, and `require`. A recipe can only `inherit` a bbclass's behavior. Whilst a recipe can both `include` and `require` include files and bbclass'es (`.inc` and `.bbclass` respectivly). Include tries to include behavior but is optionally required. This can be used for e.g. machine-specific behavior.

### Build dependencies
To build a recipe, it might depend on some build tools, libraries, or other resources. Within bitbauga, these are expressed as *build dependencies* and can be configured within a recipe with the `DEPENDS` keyword. You can only add a dependency on other recipes (`.bb` files).

### Runtime dependencies
To run a program in runtime, a resource might need implicit resources, libraries, or tools in order to function properly. These are expressed as *runtime dependencies* and can be configured within a recipe with the `RDEPENDS` keyword. You can only add a runtime dependency to other *packages*, defined by other recipes. By default, a *build dependency* that generates a *package* will be included as a *runtime dependency* as well. But this only yields true if the *package* maps to the targeted device, and the package has the same name as the *build dependency's* name.
